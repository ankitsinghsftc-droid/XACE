# NEC-012 native host and release contract

Windows x86_64, trusted creator executors, fixed64_60hz.v1. This document describes the shared service; Unity/Godot/Unreal editor and build hooks remain NEC-013/014/015. Clean-machine, signing, external tester/networking and Steam gates are not certified by same-machine process proofs.

## Release and trust

The Rust xace-player-launcher executable now accepts `--native-verify --source <release> --expected <sha256>` for read-only admission. `--native-host` additionally requires `--history <absolute persistent directory> --controller <positive id>`. The host uses inherited stdin/stdout JSON lines only. The parent supplies the reviewed SHA256 of the exact native-release.json bytes. Never read that trust value from an untrusted downloaded package and treat it as approval. No Python, cargo, compiler, Builder process or external network is required by these shipping paths.

A release contains native-release.json, executor-receipt.json, package/playable.manifest.json and all package files. The common `xace.native_release.v1` receipt fields are: schema, game_id, engine (Unity/Godot/Unreal), executor_receipt_sha256 (exact file bytes), package_manifest_sha256 (exact file bytes), compatibility, required_capabilities (sorted unique), resources (path/sha256/size records relative to release), save_schema. game_id is a stable lowercase ASCII letters/digits/hyphen/underscore identifier. Creator-side tools may produce these receipts; engine build hooks must enumerate their cooked native resources and binding/configuration receipts in resources. An empty resource inventory makes no cooked native resource claim.

Compatibility binds runtime ABI, numeric and simulation profiles, supported World versions and geometry profiles, snapshot/replay/input/event schemas and platform. The creator receipt retains locked source inventory, compiler/linker identities, offline locked recipe, two matching independent outputs, deterministic system access/scheduling census, capabilities and shipping closure. Rust verifies the pinned source-inventory declaration; it does not recompile on the player's machine. Separate creator evidence establishes that the declared builds actually occurred. The exact executable and every listed package/resource file are checked before Play and again before readiness is published. Package validation and the authoritative ticket must agree on CGS, plan, World, gameplay and presentation identities. Presentation changes are deliberately separate from the gameplay hash.

## Lifecycle protocol

After successful initial admission, the host emits xace.native_host.ready.v1 with the release identity, stopped state, save namespace and compatibility identity. Commands are single JSON lines, at most8192 bytes: play (optional preferred_port), status, stop, verify, check-save (slot). Replies have ok and result, or a refused message. A repeated Play reuses the owned authority. The assigned endpoint is loopback only; a preferred-port conflict chooses another available port. The returned ticket uses the authoritative contract and a client engine claim selected by the pinned release. The original runtime ticket is retained separately. Its credential belongs only to that local session.

The runtime is the existing authority executable and protocol, launched with --no-control. The shared Authority primitive is also used by the existing Player host; it owns a Windows Job. Stop, parent EOF and parent crash terminate only owned children. Runtime crash emits authority_lost with native_fallback:false. Native integrations must visibly freeze/stop on that event or a closed owner pipe; they must never substitute native gameplay simulation. No UI/editor integration is implied by the protocol-client proof.

The local lifecycle pipe is owner control, not a development endpoint exposed to game clients. Engine clients use existing timed input/admission on the engine socket. Session logs and tickets are retained in the explicit persistent history directory; callers must protect ticket permissions and must not place history under disposable build trees.

## Saves and updates

Save namespace: `%LOCALAPPDATA%/XACE/NativeGames/game-<game_id>/saves`. It does not depend on installation location or release version. Slots use `slot-<slot>.json`; slot names contain only ASCII letters/digits/hyphen/underscore. The xace.native_save.v1 envelope contains identity, payload_sha256 and snapshot. Identity binds game_id, save_schema, gameplay_hash, executor_sha256 and the full compatibility tuple. payload_sha256 is SHA256 of compact sorted-key UTF-8 JSON of the snapshot. Snapshot serialization/semantic validation/restoration remain runtime SaveEngine responsibilities; this lifecycle service never changes gameplay state.

check-save is read-only admission, explicitly returning restored:false. Exact compatible identity and payload digest are required. Changed schema, gameplay, executor or state profile refuses with the original bytes untouched. No automatic migration is claimed. Native save integration must check this envelope before handing the snapshot to the runtime; implementing the engine's save UI and transport is subsequent integration work. Cosmetic-only releases retain compatible save identities.

Activation happens only after a matching authoritative ticket, observed TCP listener owned by the runtime PID, validated authority readiness and successful derived-ticket publication. The per-game release-state/active.json pointer records the source and pinned release digest; previous receipts are retained with unique names. A rejected candidate or startup failure cannot replace the working pointer. Release directories are retained; explicit rollback selects the retained prior directory and its trusted digest, revalidates it and restarts it. There is no network updater, deletion of old releases, automatic in-game migration, or claim that a remote store installer is implemented. Build/update hooks must retain immutable staged releases; same-user modification of a release is detected at the next admission, not prevented by a sandbox.

## Custom gameplay proof

The unusual delayed echo graph uses the NEC-011 trusted custom ISystem, beyond the fixed generated operations. Rust admission verifies its relocated executable/package. The declared creator_echo_cli_checkpoint_replay.v1 profile accepts player graph edits and pulses, checkpoints a pending queue, rewinds and reproduces every replayed hash/event across independent runs, without player compilation. This proves the bounded CLI mechanic profile, not unrestricted mechanics, engine input-graph translation or native engine shipping.

## Verification boundaries

Actual Windows runtime processes and the existing exported Player are exercised. Three protocol clients exercise Unity/Godot/Unreal admission and authoritative ticks without a development control connection. They are not actual native editor/build tests. Resource byte verification does not replace engine-side load/animation/audio probes; NEC-011 supplies creator probes and NEC-013/014/015 must bind them to real builds. General multiplayer/off-device release gates remain unchanged. The 1,000-object NEC-017 target is unchanged.
