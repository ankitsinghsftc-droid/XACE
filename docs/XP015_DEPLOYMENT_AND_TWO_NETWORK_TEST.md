# XP-015 — Relay deployment and pending Internet acceptance

Status: public deployment and two-network acceptance are **pending by explicit owner instruction**: no hosting account/server is available. Nothing was deployed publicly. Local TLS relay proofs do not certify Internet reachability. XP-014 two-machine and XP-010 clean-machine gates remain separately pending.

The service is operator-provisioned. The current Player does not include a public XACE relay address. Once configured, users use the same Play / Invite / Join controls; they do not build code, sign into an AI service or forward a home-router port.

Operator preparation:

1. Build `xace-session-relay` from the approved source and lockfile. The tested artifact is Windows x86_64; other server platforms require their own build/run validation. Ship the Rust dependency notices alongside it.
2. Select a public TCP endpoint and DNS name. Provision a valid server certificate whose subject alternative name matches that DNS name, signed directly by the deployment CA. This initial server accepts one DER server certificate and a DER private key; clients receive the CA certificate, never the private key. Test certificates generated by `tools/xp015_relay_proof.py` are ephemeral local fixtures and must not be deployed.
3. Store a random 64-hex hosting credential in the service environment as `XACE_RELAY_OPERATOR_TOKEN`. Launch `xace-session-relay.exe BIND_ADDRESS:PORT server.der server-key.der` under a service account. The service exposes raw TLS, not HTTP/WebSocket. Public firewall/listener setup belongs on this relay server; no incoming home-router rule is required for players.
4. Provision a trusted configuration file on each Player machine and set `XACE_RELAY_CONFIG` to its absolute path in the Player/Builder process environment. Restart Player/Builder after configuration changes. The host receives its hosting credential; a recipient uses null. Protect host credentials and the service key with account/service file permissions. A relay configuration is deployment configuration, not content obtained from an invite.

Configuration shape (substitute actual deployment values):

```json
{
  "schema": "xace.relay.config.v1",
  "host": "relay.example.com",
  "port": 4433,
  "ca_der": "relay-ca.der",
  "host_credential": null
}
```

A relative CA path is resolved beside the configuration file. On the creator's configuration, `host_credential` contains the operator-issued 64-hex value. Provision the same endpoint/CA on both computers. Without this configuration the existing private-network mode remains explicitly private; a relay invitation refuses to join without trusted relay configuration. The relay is trusted to see forwarded traffic; TLS protects the network links, not traffic from the operator.

Two-network acceptance:

1. Use two ordinary, separate Internet connections (for example home broadband and a separate mobile hotspot), the same verified Player release, and the provisioned relay. Record endpoint, OS/release hashes, network types and RTT. No developer tools or AI account on the recipient, and no manual home-router forwarding.
2. Host Play, issue an invite, and join from the recipient with no cached game package. Observe verification/progress and both Players reaching Playing. Capture encrypted network traffic and record the host journal's matching session/incarnation, distinct player IDs and verified baseline records. Confirm only the creator runs this session authority.
3. Drop the network link briefly while retaining the relay process. Verify fencing, reconnection using the same player identity, increased connection generation and a newly verified baseline before inputs resume. Host session/incarnation and process identity must remain unchanged.
4. Stop/restart the relay. Verify visible interruption, removed remote input membership and no silent plaintext fallback or second authority. The documented in-memory profile requires ending/restarting the session after lost relay state.
5. Exercise expired/replayed invitations, wrong CA/hostname, attempted control/arbitrary-target routing, oversized frames, connection/session saturation and traffic budgets. Capture refusals without sharing live credentials.
6. Leave/end and close/crash the host. Verify client/cache/process cleanup, closed tunnels and bounded relay state expiry; retain the authoritative journal.

Record failures and measured availability/latency limits. A slow client unable to acknowledge a current XP-013 baseline remains fenced; do not report the Internet gate passed until actual remote Players complete the workflow. A local proxy, loopback TLS or two windows on this machine is insufficient evidence.

Local reproduction: build the relay and launcher, export the Player using `tools/xp010_player_distribution.py`, then run `python tools/xp015_relay_proof.py --release RELEASE_FOLDER --out NEW_PROOF_FOLDER`. The proof uses local OpenSSL only to create test credentials; recipient Player processes have development tools removed from PATH. The local proof records pending public acceptance explicitly.
